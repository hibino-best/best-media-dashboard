## 2. 作業の手順（必ず守る）

### デプロイ（Webアプリ）
1. 変更前にバックアップを scratchpad に取る（大きい変更のとき）。
2. **`node --check public/app.js` と `node --check server.js`（と変更した .js）を別々に実行**。`&&` でつないで片方が飛ばされないようにする。
3. 画面を変えたら `public/index.html` の `?v=N` を必ず上げる（キャッシュ対策）。
4. `webapp/system-map.json` の `version` を `1.<N>`、`updated` を日付にし、`changelog` の先頭に1件追加。**個人名は書かず、「どの項目を調整したか」だけの短文（例：「KW追従の表を調整」「公開記事一覧に「INDEX」の列を追加」。40字以内）**（2026-10-28 ユーザー指定）。仕組み（スケジュール・流れ・保存先）が変わったら該当箇所も直す。
5. テスト画面で確認：`.claude/launch.json` の `dashboard-dev-test` を起動 → http://localhost:5178/dev-test/index.html （ダミーAPIは `webapp/dev-test/index.html` 内）。
6. デプロイ：`& "$env:LOCALAPPDATA\Google\Cloud SDK\google-cloud-sdk\bin\gcloud.cmd" run deploy best-media-dashboard --source . --region asia-northeast1 --project bestmedia-510909 --quiet`（`webapp` で実行）
7. 本番URLを開き、ログイン画面が出て新しい `app.js?v=N` を読んでいることを確認してから報告。

### GAS
- 反映：`gas` で `& 'C:\Program Files\nodejs\node.exe' 'C:\Users\yoshi\AppData\Roaming\npm\node_modules\@google\clasp\build\src\index.js' push --force`
- **ユーザーに実行を頼むときは、毎回「エディタのURL・ファイル名・関数名・手順（再読み込み→ファイルを開く→関数を選ぶ→実行）」をセットで書く。**
- 実行結果は `gcloud logging read "resource.type=app_script_function" --freshness=30m --project bestmedia-510909` で読める。GASは1回6分まで。
- clasp / gcloud のログインは会社アカウントの再認証（invalid_rapt）で切れる。ユーザーの端末（ターミナルパネル）で `npx -y @google/clasp login`、`gcloud auth login --force`（ブラウザ方式。URLの貼り付け方式は失敗しやすい）。

### パッチの書き方の注意
- 置換スクリプトを1行に詰めるとき、`//` コメントは使わず `/* */` を使う（行の残りを消して画面が真っ白になった事故あり）。
- `node -e "..."` の中の正規表現・バッククォートはエスケープが崩れやすい。scratchpad にスクリプトファイルを書いて実行するか、Edit ツールを使う。
- BigQuery の列 `no` は予約語なのでバッククォートで囲む。

## 3. 守ること（ユーザーとの決めごと）
- **スプレッドシートには書き込まない**（読み取りのみ。設定タブの行の自動追加・削除だけ例外）。画面での修正は Firestore に保存し、取り込みより優先。
- **APIキー・トークン・パスワードはチャットに貼らせない・出さない**。画面の入力欄 → Secret Manager。
- kintone は個人情報（お客様名・カナ・電話・メール・郵便番号・町名・番地・建物名）を取らない。住所は市区町村まで。
- 定期実行・自動化を新しく作るときは、方式（クラウドのルーティン／アプリの Scheduled／タスクスケジューラー＋`claude -p`）をユーザーに確認してから（Cloud Scheduler の追加も事前に説明）。
- ユーザーへの返答は日本語・やさしい言葉で、表や箇条書きを使って簡潔に。数字の比較は表で。
- ユーザーの指示で決めたルールは、コードにも `（YYYY-MM-DD ユーザー指定）` とコメントを残している。

- 進行管理などのデータ（Firestore の article_overrides・contracts・sheet_accepts・press_overrides など）を直すときは、ユーザーの「OK」をもらってから。直す前の値は残す（sheet_fix_logs・contracts の history・scratchpad）。

### 画面（ダッシュボード）
- メディア数値／コンテンツ作成（制作状況・コンテンツ進行管理・プレスリリース進行管理・月次進行管理・KW追従・カテゴリ・タグ・ブロック）／報酬管理／支出情報（支出一覧・BEST人件費・サイト制作・修正費・業務委託費・プレスリリース費・ツール利用費）／収益情報／目標・工数。管理メニューは「BEST MEDIA管理」（ユーザー・メディア・契約・定額のサービス・API・連携設定・システム構造など）と「全体管理」（タスク通知・BEST社員管理・REsta社員管理・メディア担当管理・AIからのアクセス）。
- 主なファイル（webapp/）：press.js（プレスリリース）、invoices.js・invoice_pdf.js（請求書）、expense_invoices.js（支出の請求書の取り込み）、subscriptions.js（定額のサービス）、ai_costs.js（AI の API の費用）、staff.js（BEST社員・人件費・メディア担当）、resta.js、copycheck.js（コピペチェック・原稿の文字数）、index_check.js、gmail.js（メール送信）、feedback.js、person_links.js、ai_guard.js。
- 定期実行（上の6つのほか）：`index-check` 毎日4:40、`invoice-stale` 毎日9:00、`invoice-unrequested` 毎月3日0:00。

### 権限・見え方
- 役割：管理者・BEST役員・正社員・契約社員・アルバイト・業務委託ディレクター／AD／アシスタント兼ライター／ライター・監修者・契約外ライター・BEST経理部（finance）・REsta社員（resta）。業務委託・監修者は契約中の契約の担当メディア・ディレクトリだけ見られる（applyRole）。
- コンテンツ作成：ライター（out_writer・free_writer）は月次進行管理だけ（自分の記事だけ、直せるのはライティングURL・文字数・画像枚数・進行状況・アップロードURL・アップロード日）。業務委託のディレクション担当はプレスリリース進行管理を見るだけ。監修者は月次進行管理を見ない。
- 生年月日・給与・賞与・評価・人件費は**フル管理者だけ**。REsta社員・経理部には収益・支出・目標・工数を出さない。

### 記事・進行管理
- 本数はアップロード日の月で数える。執筆担当を入れたら「アップロード目標月」（target_ym）が必須。月次進行管理は目標月ごと（なければアップロード日の月）。
- 担当者名は担当者の紐づけ（person_links）で正式な名前にそろえる。ディレクション担当・監修担当が空の記事は、メディア担当管理の担当で補う（表示だけ）。

### 報酬・請求
- 報酬＝契約の単価 × 担当記事（記事単価／文字単価／画像・アップロード・監修・ディレクション費・稼働表の時間・プレスリリース）。月はアップロード日の月（記事ごとの請求月 bill_ym があればそれ）。過去の月は契約管理シートの請求と照合し、合わない月は「差異ありでOK」（sheet_accepts）でシートの金額を使う。
- 画面での請求は **2026年11月分から**（INVOICE_START）。流れ：請求者 → 請求担当（メイン・サブ）が確認 → 管理者が経理部（finance@）へ送る → 経理部が確認 → 完了でリコーへ自動送信。消費税10%、源泉は個人だけ10.21%（100万円超は20.42%）、支払期日は翌月25日。

### 支出（すべて税抜き・ドルは月末レートで円）
- 支出一覧は SEO数値管理シートではなく各タブの計算を合計：BEST人件費（給与＋賞与÷6 を稼働%で配分。PM・プレスリリース・サポートなど共通の担当はその月にあるメディアで均等）、業務委託費（報酬管理一覧と同じ支払額。サイト作成・修正の契約は除く）、サイト制作・修正費（契約管理シートのテクノグラム・businessbay＋確定した請求）、プレスリリース費（リリースごとの調査費＝Freeasy・配信費＝PR TIMES。支出の請求をリリースに紐づけできる）、ツール・AI費（定額のサービス・AI の API・確定した請求。メディアへは Ahrefs の順位追跡のKW数の割合）。
- ディレクトリ単位では、ディレクトリが決まらない分をそのメディアのディレクトリで均等に分ける。

### 作業のコツ
- 画面の描画は非同期。読み込みのあとに `renderSeq` が変わっていたら書き込まない（古い描画の上書き防止）。
- press_overrides のドキュメントIDは encodeURIComponent(リリースID)（REST では二重に encode）。article_overrides の ID は sha1(`メディア|no<No>`)。
- ユーザーの PC では gcloud の ADC がないので、ローカルの確認スクリプトは `gcloud auth print-access-token` のトークンを OAuth2Client に入れて Firestore・BigQuery を読む（scratchpad に置く）。
